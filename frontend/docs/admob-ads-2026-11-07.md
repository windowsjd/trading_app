## 공통 런타임 (`features/ads/adsRuntime.native.ts`)

이 빌드에 단위가 있을 때만 네이티브 모듈을 불러온다 → UMP `gatherConsent()` → `canRequestAds`가 참일 때만 SDK 초기화(테스트 모드에서만 에뮬레이터를 테스트 기기로 지정). 앱 세션당 한 번, 실패는 기억하지 않아 다음 화면이 다시 시도한다. 개인정보 선택이 필요하면(`privacyOptionsRequired`) 자금 관리 시트에 `광고 개인정보 선택` 버튼이 나타난다. 광고 요청은 모두 비개인화(`requestNonPersonalizedAdsOnly`)이며 ATT는 요청하지 않는다.

## 보상형 광고 흐름 (`GeneralRewardSheet`, `features/adRewards/rewardedAd.native.ts`)

1. `광고 보고 받기` / (확인 후) `광고 보고 초기화` → 새 멱등 키로 **서버 세션 생성**(`POST …/ad-rewards/sessions`). 서버가 지금 거절할 명령(차단된 초기화, 기능 꺼짐 등)이면 광고를 띄우지 않고 그 사유를 보여 준다.
2. 세션의 `ssv`(userId, customData)를 넣은 새 광고를 불러와 로드되면 바로 표시. 상태 문구: 준비 중 → 불러오는 중 → 시청 중 → 시청 확인 중.
3. 끝까지 보고 닫으면(`earned`, 보상 후 SDK 오류도 포함) 같은 키·`proof: sessionId`로 기존 claim/reset 명령. `AD_REWARD_VERIFICATION_PENDING`(Google 확인 전)이면 2초 간격으로 약 30초 같은 명령을 다시 묻고, 그래도 아니면 **확인 대기**(결과 확인 버튼). 시트를 닫거나 계정을 바꿨다 돌아와도, 광고 중에 홈이 시트를 다시 마운트해도(같은 로그인·계정) 대기 시도를 유지하고 다시 열 때 한 번 재확인한다(앱 프로세스 메모리 — 앱을 완전히 종료하면 사라진다). 서버는 Google 콜백이 오면 앱과 무관하게 스스로 지급/초기화한다. 콜백이 **기록된 뒤** 서버 장애(DB 오류 등)로 지급/초기화가 끝나지 못하면, 앱이 꺼져 있고 Google 재시도가 끝났어도 서버 복구 작업이 같은 명령으로 다시 처리한다(2026-11-08: 1분 뒤부터 최대 1시간 간격, Google 확인 후 24시간까지, 한 번만 지급·초기화; 제품 규칙상 거절된 명령 — 차단된 초기화 등 — 은 자동으로 다시 실행하지 않는다. 서버 계약 문서의 `Server recovery`). 앱 쪽 동작·API 응답은 바뀌지 않는다. Google 재시도 내내 **기록조차** 되지 못한 콜백만 남지 않는다(돈은 움직이지 않음).
4. 구분 표시: 조기 종료(아무것도 처리 안 함), 로딩 실패, 표시 실패, 동의로 인한 불가, 다른 광고 표시 중, 서버 거절(서버 사유), 응답 유실(같은 키 재확인).
5. 연타 방지: 동기 ref 가드 + 버튼 loading/disabled. 광고 객체는 시도마다 새로 만들고 끝나면 모든 구독을 해제한다. 앱 전체에서 보상형 광고는 한 번에 하나.
6. 개발·미리보기 빌드는 샘플 보상형 단위를 쓰므로 Google SSV 콜백이 우리 서버로 오지 않는다 → 지급되지 않고 확인 대기에 머문다(테스트 광고로 실제 보상 없음). 광고 표시 흐름 확인은 가능하다(서버가 광고 기능을 켠 개발 백엔드 필요).

## 배너 (`components/ads/BannerAdSlot.native.tsx`)

- 위치: 홈 맨 아래(본문 다음, 하단 탭바 바로 위 — 일반·초보·시즌 공통), 커뮤니티 피드 맨 아래(커뮤니티 탭과 시즌 리그 › 커뮤니티 공통). 커뮤니티의 `글쓰기` 버튼은 목록 영역 안에 있어 배너 상단에서 24dp 위에 떠 있고, 배너는 목록·버튼·시트 위에 겹치지 않는 별도 띠다(상단 1px 구분선 + surface 배경).
- 고정형 적응형 배너(`ANCHORED_ADAPTIVE_BANNER`), 화면 폭 기준 높이는 SDK가 정한다. 광고가 도착하기 전에는 공간을 차지하지 않는다(높이 0) → 로드 후 한 번 레이아웃이 늘어난다.
- 로딩 실패 시 그 자리를 비우고, 앱이 포그라운드로 돌아올 때만 한 번 다시 시도(재시도 루프 없음). iOS는 포그라운드 복귀 시 표시 중인 배너를 다시 로드(라이브러리 권고). 슬롯당 배너 하나, 언마운트 시 구독 해제. 보상 API와 무관.
- 참고: 16.3.4 타입에서 `ANCHORED_ADAPTIVE_BANNER`는 `LARGE_ANCHORED_ADAPTIVE_BANNER` 권장으로 deprecated 표시가 있다. 사용자 요구(고정형 적응형)와 화면 공간 때문에 표준 크기를 유지했다. 대형으로 바꿀지는 실기기 화면 확인 후 결정할 사항이다.

## 배포 전 확인 (사용자 작업)

1. AdMob 콘솔: 앱 ID(Android `~9002185139`, iOS `~7288069200`)가 각 스토어 식별자(Android `com.nanghwa.tradingclass`, iOS `com.leagueoftrading`)와 연결돼 있는지, 위 4개 단위의 유형(보상형/배너)과 플랫폼이 표와 같은지.
2. **보상형 두 단위만** SSV 콜백 URL `https://<API 호스트>/api/v1/ad-rewards/admob/ssv` 설정 후 "Verify URL"(서버가 배포된 뒤). 보상 아이템 이름은 `&`·`=` 없이(예: `virtual_krw`) — 들어 있으면 서버가 모든 콜백을 400으로 거절한다(서명·파싱 불일치 방지 규칙).
3. UMP 메시지(지역별 동의/개인정보 선택)를 AdMob 콘솔에서 게시. 앱은 UMP 결과를 따른다.
4. Google Play: 광고 포함 표시, Data safety(광고 SDK 수집 항목). App Store: App Privacy(광고 SDK), SKAdNetwork(`cstr6suwn9` 포함 여부 확인), ATT 미사용과 일치하는지.
5. 네이티브 코드·SDK(16.3.4)·권한은 바뀌지 않았지만, 광고 모드(`extra.adMob`)는 빌드 시점에 찍히므로 **새 EAS 빌드**(preview/production)가 필요하다. 기존 운영 빌드는 `mode: disabled`라 OTA로 JS만 보내도 광고가 나오지 않는다.
6. 실기기 확인(공개 출시 전): 서버는 `AD_REWARD_ENABLED=true`일 때만 광고 세션을 열므로, 새 production 빌드를 **내부 배포만**(Play 내부 테스트·TestFlight) 한 상태에서 Render 광고 값을 켠다. 스토어의 기존 빌드는 `mode: disabled`라 광고를 띄울 수 없고, 지급은 어떤 경우에도 Google 서명 콜백이 있어야 한다. 내부 빌드로 Android·iOS 각각 충전 1회(+초기화 1회) → 서버 로그 `admob_ssv_callback … REDEEMED` → 지갑 +500만 원·`ad_reward` 원장 1건 확인. 운영 단위로 시험할 때는 기기를 AdMob 테스트 기기로 등록(자기 실광고 클릭 금지); 테스트 광고에도 SSV 콜백이 오는지 그때 확인하고, 오지 않으면 실광고 1회 시청(클릭 없이). 문제가 있으면 `AD_REWARD_ENABLED=false`(콜백 없이는 돈이 움직이지 않는다). 확인 후에만 공개 출시.
