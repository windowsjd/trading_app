# KOSCOM 과거 분봉·호출 한도 조사 — 실제 조회 대기

조사 기준: 2026-10-12, Asia/Seoul. **코드 검토·날짜 선정·진단 도구의 모의 검증은 완료했으나 실제 KOSCOM 조회는 0회다. 과거 제공 범위와 계약별 호출 한도는 아직 검증되지 않았다.** Render 서비스 메타데이터를 읽는 권한으로 Shell 실행 권한을 대신할 수 없었다. 아래 결과표의 ‘미실행’을 공급자의 ‘데이터 없음’으로 해석하면 안 된다.

### 명세 접근 및 코드 대조

사용자가 지정한 `3-1) 정보이용계약별 API서비스 제공내역(250103)` 및 `3-2) 20240701_OPEN API 금융정보 조회 명세(spec)_v3용_v3.13` **원본은 저장소·접근 가능한 attachment 및 파일 검색에서 찾지 못했다.** 과거 구현 문서가 이를 참조한다는 사실을 원본 재검토로 계산하지 않았다. 계약에서 허용되는 API 목록·보존 범위·실제 허용량은 미확인이다.

대신 KOSCOM 공식 공개 문서에서 다음을 확인했다.

- 일중 경로, 주기 `60`/`600`, `inqStrtDd`, `strtTm`/`endTm`의 HHMM 형식, 100건 상한, `hisLists` 및 일중 OHLCV 필드는 현재 코드와 일치한다. 공개 예제에는 행별 날짜가 없다. 분봉 보존 일수나 과거 날짜 필터의 보장은 발견하지 못했다. [주식실시간A](https://koscom.gitbook.io/open-api/api/marketv3/stocks/stocksa)
- 일봉 `history`는 D 주기와 시작일·종료일·요청 건수 및 행별 `trdDd`를 사용한다. 진단에서는 같은 시작일·종료일, `reqCnt=1`로 96거래일 전 일봉만 요청한다. [주식실시간종가A](https://koscom.gitbook.io/open-api/api/marketv3/stocks/closeda)
- 상용과 Sandbox Gateway를 공식 목록과 대조했다. 도구는 기존 코드의 두 HTTPS origin만 허용하고 환경변수에 설정된 환경을 그대로 사용한다. [API 서비스](https://koscom.gitbook.io/open-api/api)
- 개별 endpoint의 예제는 인증 헤더를 사용하지만, 플랫폼 공통 설명은 GET의 `apikey` 쿼리 방식을 명시한다. 현재 클라이언트는 공통 설명과 일치한다. 이 공개 문서 내부 차이를 기록했으며 요청 중 인증 방식을 바꾸거나 재시도하지 않는다. [API 테스트 절차](https://koscom.gitbook.io/open-api/how-to-use/devcenter)

일중 문서에는 날짜 형식이 `YYYYMMSS`로 적힌 부분과 일요일인 `20220501`을 사용하는 예제가 있다. 이를 새로운 날짜 형식·과거 휴장일 데이터 제공의 증거로 채택하지 않았다. 기존 코드 및 history의 8자리 `YYYYMMDD`를 유지한다. `inddTm`의 시작/종료 의미도 명시적으로 보장되어 있지 않다. 첫 10분 예제의 09:10 때문에 기존 adapter가 종료 시각으로 해석하지만, 이는 구현의 추론이다. [주식실시간A](https://koscom.gitbook.io/open-api/api/marketv3/stocks/stocksa)

### 날짜 선정

시각 확인은 `2026-10-12 12:43:01 UTC` = **21:43:01 KST**였다. 따라서 10월 12일 정규장이 완료된 상태를 기준으로 잡았다. 달력일이 아닌 거래 세션 배열에서 정확히 0·1·30·60·96개 전을 선택했다.

사용 달력은 저장소의 [KRX_2026](../../../backend/src/orders/market-calendar/data/krx-2026.ts), 버전 `2026.1`, 기록된 검증일 `2026-07-13`, 2026년 전체 coverage다. 표준 거래일 판정 및 휴장 기록을 사용했고 모든 대상 날짜에는 특별 시간 override가 없다. 공개 KRX 정규장 09:00–15:30 기준에서도 10:00–11:00은 세션 안에 있다. [KRX 거래시간·휴장 기준](https://global.krx.co.kr/contents/GLB/06/0602/0602020204/GLB0602020204T1.jsp)

계산 구간에서는 5/25, 6/3, 7/17, 8/17, 9/24, 9/25, 10/5, 10/9와 모든 주말을 제외했다. 새 휴장으로 누락되기 쉬운 6/3·7/17은 공급된 달력에 이미 반영되어 있고, 공식 금융기관의 추가 휴장 공지와도 대조했다. [삼성선물 공지](https://www.ssfutures.com/ssf/customer/notice/CUS_01102.cmd?ND_PATH=%2Fbiz%2Fcustomer%2Fnotice%2FAd202_4589.shtm&categoryID=M158746897264671332), [삼성증권 공지 검색 내용](https://www.samsungpop.com/sscommon/jsp/search_ux/search.jsp?query=%EC%8B%A0%EC%A3%BC%EC%88%98%EA%B6%8C%EC%A6%9D%EC%84%9C)

진단에 복사한 휴장 배열이 저장소 달력의 휴장 배열과 같은지 별도로 검사하고 원본 파일 해시를 [calendar-plan.json](evidence/calendar-plan.json)에 기록했다. KRX 웹의 연간 달력은 동적 화면이라 2026년 전체 원문을 이번 브라우저로 다시 읽지는 못했다. 저장소의 검증된 연간 자료를 사용했으며 이후 임시 휴장·운영 override까지 실시간으로 검증했다고 주장하지 않는다.

요청 11은 휴장일 **2026-10-09**의 1분봉, 요청 12는 **2026-05-19**의 일봉 대조로 고정했다. 둘 다 미실행이다. 일봉 실패 후 추가 요청을 만들지 않는다.

진단 출력에는 HTTP/API 상태, 원본 행 수·유효 행 수, 처음·마지막 시각, OHLCV 유효성, 중복/충돌, 응답의 오름/내림/비단조 순서, 시간 간격 이상, 조회 창·정규장·주기 경계 이탈, 날짜 필드 유무·일치 여부, 날짜를 제외한 정규화 데이터 해시가 포함된다. 원문 응답이나 전체 행은 출력하지 않는다.

날짜별 해시가 반복되거나 휴장일에 유효 캔들이 있으면 날짜 필터 의심 증거로 남긴다. 가격이 다르거나 일봉 범위 안에 있다는 사실만으로 과거 귀속을 확정하지 않는다. 행별 날짜가 없으면 **‘데이터 존재·날짜 미확정’**으로 남기며, result의 날짜 하나만 일치해도 이 판정을 유지한다. 행별 날짜가 모두 일치하고 휴장일 대조가 성공하고 반복·모순이 없어야 도구의 잠정 ‘확인됨’ 후보가 된다. 최종 판정에는 공급자 필드 의미에 대한 검토가 추가로 필요하다.

성공한 빈 응답은 ‘정상적인 데이터 없음’, 인증/계약 오류는 ‘권한 부족’, 429·호출 한도 오류는 ‘호출 제한’, 형식·날짜·정합성 오류는 ‘검증 실패’로 기록한다. 빈 날짜 한 건만으로 더 오래된 전체 구간을 ‘제공 불가’로 선언하지 않는다. 이 단계에서 ‘제공 불가 추정’도 부여하지 않았다.

## C. OHLCV 정합성

**실제 1분봉·10분봉 비교, 가격·거래량·거래대금 일치 여부는 모두 미확인이다.**

도구는 1분/10분 라벨 각각 START/END의 네 조합에서 같은 실제 10분 구간에 속하는 1분봉 열 개만 합성한다. 시가=첫 봉, 고가=max, 저가=min, 종가=마지막 봉, 거래량·거래대금=sum이다. 조회 창 밖 경계 구간은 제외하고, 구성 분봉이 하나라도 없으면 해당 구간을 비교하지 않는다. 금액은 숫자 토큰을 문자열로 보존한 뒤 BigInt 기반 고정 소수 계산을 사용해 비교한다.

가설별 완성·누락·경계 제외 구간 수 및 여섯 필드의 불일치 횟수를 출력한다. **가설 계산은 시각 의미 확인의 증거이며 최종 ‘정합성 확인’ 판정이 아니다.** 도구의 boundary는 `UNCONFIRMED`, 최종 비교 상태는 ‘비교 불가’로 유지한다. 공식 명세/공급자 확인 또는 충분한 실제 경계 증거가 필요하다. HHMMSScc 외 형식, 초·소수초가 있는 분봉 라벨도 임의로 맞추지 않는다.

모의 검증에서는 START/START와 END/END의 6개 구간·OHLCV 여섯 항목이 정확히 일치했고, 누락된 분봉의 구간 제외와 거래량·거래대금의 1단위 차이도 탐지했다. 이는 도구의 계산 검증이며 실제 KOSCOM 품질 결과가 아니다.

| 계약상 intraday/history 사용 권한 | 미확인: 원본 계약 자료 및 실제 응답 미확보 |

공식 문서는 위 두 헤더를 일일 한도·남은 허용량으로 설명하며 **09:00에 초기화**한다고 적고 있다. 문서 예시의 50,000을 이 계약의 실제 한도로 사용하지 않는다. API 종류별 제한이라고 설명하므로 같은 key의 모든 endpoint가 하나의 공통 예산을 공유한다고도 단정하지 않는다. [KOSCOM Rate Limiting](https://koscom.gitbook.io/open-api/rate-limiting)

진단은 각 응답의 quota/rate-limit/retry-after 관련 헤더 **이름**과 숫자 값만 추출한다. 기타 값은 존재만 표시하고 원문을 생략한다. 이름만으로 의미를 알 수 없는 헤더는 별도 미확인 항목이다. 연속 응답의 remaining 차이는 문자열 정수로 계산하되, 운영 수집의 동시 요청·endpoint별 예산·reset·한도 변경 가능성 때문에 진단 1회의 차감이라고 단정하지 않는다. 첫 응답 전 남은 양을 얻기 위한 추가 호출도 하지 않는다.

## E. Trading Class 적용 가능성

1. **과거 1분봉 범위:** 이번 조사에서 실제 확인된 과거 범위는 없다. 30/60/96거래일 후보는 선정했지만 호출 결과가 없다. 현재 adapter의 ‘당일만 요청’은 앱의 신뢰 정책이며 공급자의 최대 보존기간이 아니다.
2. **과거 10분봉 범위:** 실제 확인된 범위는 없다. 문서의 600 주기 지원을 96거래일 보존 보장으로 확대 해석하지 않는다.
3. **최초 96거래일 전 4시간봉 확보:** 현재는 판단 불가. 한 날짜의 한 시간 데이터가 성공하더라도 97개 세션 전 구간, 누락 분봉, 경계·동시호가, 상용 환경, 전체 100종목까지 확보된 것은 아니다. 날짜 귀속 검증과 전체 세션 가용성 근거가 필요하다.
4. **5분·15분·30분·1시간 원천:** 1분봉을 각각 3·7·13·25개 거래 세션(당일 포함)에서 확보해야 현재 5분봉 합성 방식으로 구현할 수 있다. 표본 5개 날짜의 결과만으로 사이에 있는 모든 세션까지 충분하다고 보장할 수 없다. 10분봉은 30분·1시간의 후보 원천이 될 수 있지만 5분/15분을 정확히 분해·합성할 수 없다.
5. **5분봉 합성 구조 유지:** 기존 정확한 1분→5분→상위봉 계산 구조를 유지할 근거는 있다. 다만 현재 당일 제한과 기본 35달력일 보존으로 신규 96거래일 표시 정책을 충족한다고 결론낼 수는 없다. 운영 보존 설정을 읽지 않았으며 실제 변경도 하지 않았다.
6. **10분봉 별도 활용:** 1분 과거 범위가 짧고 10분 범위가 충분한 경우, 30분·1시간·4시간의 과거 원천 후보로 검토할 이유가 있다. 같은 세션 기준과 OHLCV·날짜 귀속이 검증되어야 한다. 10분봉을 쪼개 가상의 5분봉을 만들면 안 된다. 이번에는 별도 저장·수집·read 로직을 구현하지 않는다.
7. **100종목 초기 수집 제약:** 단일 종목·단일 날짜·1시간 표본은 종목별 보존 차이, 신규 상장/거래정지, 전체 세션 빈 구간을 증명하지 못한다. intraday는 단일 종목 경로이며 현재가/호가의 최대 20종목 batching을 적용할 근거도 없다. 아래는 제공이 가능하다는 가정에서의 계산 예산이다.
8. **지속 수집 한도 위험:** 현재 native minute 갱신 방식이 100종목으로 확장되면 정상 390분 세션에서 약 39,000 intraday 요청/일이 발생할 수 있다. 현재가·호가·목록·닫힌 세션 회복·중복 창·실패 재시도도 더해진다. 실제 계약 예산을 관측하기 전에는 polling 간격이나 수집량 변경을 결정할 수 없다.

### 요청 규모 계산 — 실행·계약 보장 아님

정상 09:00–15:30 전체 세션 390분, 100종목, **96거래일 전부터 당일까지 = 97세션**을 가정했다. 현재 동시호가 누락 정책이나 실제 데이터 수에 따라 달라지며 초기 수집을 실행한 값이 아니다.

| 가정 | 요청 규모 |
| --- | --- |
| 1분봉 390개/종목/세션, 한 번에 최대 100개를 모두 효율적으로 반환 | 이론상 최소 4회 × 97 × 100 = **38,800회** |
| 현재 95분 창 방식을 과거에도 적용할 수 있다고 가정 | 5회 × 97 × 100 = **48,500회**; 당일 제한을 해제한 것이 아님 |
| 10분봉 39개/종목/세션을 날짜당 1회에 모두 반환 | 1회 × 97 × 100 = **9,700회**; 실제 반환/창 동작 미검증 |
| 일봉 576거래일 전부터 당일까지, 100행씩 정상 paging | 6회 × 100 = **600회**; 이번 검증의 대상은 한 날짜 한 행뿐 |
| 1분봉 지속 갱신 100종목 × 390분 | **39,000회/정상 세션**; 실패·추가 회복 호출 제외 |

3초마다 현재가·호가를 모두 폴링하고 100종목이 KOSPI/KOSDAQ에만 있다고 가정하면, 한 주기에는 `2 × (ceil(KOSPI종목수/20) + ceil(KOSDAQ종목수/20))` 호출이다. 10~12회/주기, 390분 세션에서는 78,000~93,600회다. 분봉 39,000회를 더하면 117,000~132,600회/세션의 **설정 가정치**가 된다. 실제 polling 활성화/간격/정지 시간/종목 분포/endpoint별 quota는 미조회이며 현재 운영량이라는 뜻이 아니다. 앱 기본 polling OFF를 바꾸지 않았다.

## F. 최종 결론 및 실행 인계

현재 최종 상태는 **‘과거 분봉 확보 범위의 추가 검증 필요’**, 그리고 **‘계약 또는 호출 한도에 관한 추가 확인 필요’**다. ‘기존 수집 구조로 충분’이나 ‘공급자 제공 범위상 최초 확보 불가능’을 선택할 실제 증거는 아직 없다. 현재 코드의 당일 제한·기본 보존기간은 새 정책을 위한 별도 검토 대상이지만, 조사 범위에서 변경하지 않았다.

### 기존 Render Shell에서 실행

1. [기존 trading_app 서비스](https://dashboard.render.com/web/srv-da84cg8u01pc73cjasa0)를 열고 **Shell** 탭을 연다. 새 서비스·새 배포·ephemeral instance를 만들지 않는다.
2. [render-shell-command.sh](render-shell-command.sh)의 **파일 내용 전체**를 복사해 Shell에 한 번 붙여 넣는다. 이는 완전한 실행 명령이며 Render에 이 파일이나 저장소의 로컬 진단 파일이 존재할 필요가 없다. 압축된 검토 코드가 명령 안에 포함되어 있고 해시 검사 후 메모리에서 실행된다. npm 설치·파일 업로드·git pull이 필요 없다.
3. 여러 줄 붙여넣기가 깨지는 터미널이라면 [render-shell-one-line.sh](render-shell-one-line.sh)의 **한 줄 명령 전체**를 대신 사용한다. 두 명령은 같은 코드·계획이므로 **둘 다 실행하면 안 된다**. 어느 형식도 외부 URL에서 코드를 다운로드하지 않는다.
4. 기존 `KOSCOM_API_KEY`, `KOSCOM_BASE_URL`을 읽는다. 출력/입력/수정하는 단계가 없다. [Render가 제공하는 서비스 ID](https://render.com/docs/environment-variables)를 비교해 지정된 서버가 아니면 요청 전에 중단한다. Node 22 이상 및 lossless JSON 기능도 먼저 검사한다.
5. 날짜는 **2026-10-12 장 종료 후 계획으로 고정**했다. 다른 KST 날짜나 종료 전이면 `PLAN_DATE_STALE_OR_NOT_CLOSED`로 금융 API 요청 없이 중단한다. 이 경우 계획을 다시 검토해야 하며 날짜·host·인증·파라미터를 임의 수정하거나 강제 실행하지 않는다.
6. 정상 실행은 JSONL의 `start` 1줄, `request` 최대 12줄, `summary` 1줄을 출력한다. 각 request에 HTTP·API·행·시각·검증·quota 정보가 들어간다. start의 `baseEnvironment`가 TEST이면 Sandbox 검증이며 상용 제공 범위로 일반화할 수 없다. [Sandbox 데이터 의미](https://koscom.gitbook.io/open-api/how-to-use/devcenter)
7. **공유할 내용은 이 진단의 `start`·`request`·`summary` JSON 줄뿐**이다. `fatal`이 있으면 그 진단 줄도 함께 공유한다. 환경변수 화면, 키, Shell의 다른 출력, curl 원문 응답을 공유할 필요가 없다. 자동 분석은 항상 `actualApiValidationComplete:false`로 출력하며, 결과를 받은 뒤 사람이 날짜·시간 경계를 검토해 보고서 판정을 확정한다.
8. 실행 중 **Ctrl+C**로 중단한다. 이 독립 Node 요청이 취소되고 이후 요청을 시작하지 않으며 가능한 경우 부분 summary를 출력한다. 호출이 서버에 도달한 뒤 취소하면 공급자가 이미 차감했을 수 있다. `summary.actualCalls`는 시작한 요청 수다. 401/403/429, API 오류, timeout/transport/응답 이상, remaining-day 0이면 추가 호출 없이 중단한다.

재실행 방지를 위해 실제 진단 실행 시 `/tmp/trading-class-koscom-history-20261012.once`라는 작은 **진단용 표식**만 만든다. 앱 설정·DB·Redis에는 쓰지 않는다. 성공/실패/중단 뒤에도 남겨 두며 삭제·재시도하지 않는다. `/tmp`는 인스턴스 간 공유 예산이 아니므로 다른 Shell/인스턴스에서도 반복 실행하면 안 된다. 입력 중단·오류가 있었다면 현재 출력부터 공유해 총 호출 수를 먼저 확인한다.
