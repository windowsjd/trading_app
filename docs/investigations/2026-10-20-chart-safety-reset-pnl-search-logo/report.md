## A. Binance 선물 차트 호출 안전성

### A-0 구조 확인 (요청서 기술과 실제 구현 비교)

요청서의 구조 설명은 실제 코드와 일치한다. 차이·보충할 점:

| 항목 | 실제 구현 |
| --- | --- |
| 분당 상한 | 프로세스별 **슬라이딩 60초**, 요청 시각 기준으로 "큐에 들어간 호출" 수를 센다(완료 수가 아님). 같은 키의 진행 중 호출에 합류한 요청·유효 캐시 응답은 세지 않는다. 기본 60, 1..600 밖이면 부팅 거부 |
| 대기 | 캐시가 있는 시청자는 최대 2초 뒤 stale 사본, 없는 시청자는 최대 8초 뒤 503 `FUTURES_CANDLES_UNAVAILABLE`. 갱신 호출은 끝까지 진행되어 다음 폴링에 쓰인다 |
| 순차 실행 | 한 번에 하나, **이전 호출 종료 후** 150ms. 끝나지 않는 호출은 15초 뒤 차례를 넘긴다 |

| 조정기 우선순위 | **수정 전에는 우선순위가 없었다**(선착순). 아래 A-4의 실제 문제 원인 |

### A-1 동일 차트 요청 병합 — 이상 없음

`backend/src/assets/market-candle-futures-provider.safety.spec.ts`(신규, 운영 설정 120·150ms·2초·8초·15초, Jest 가짜 시계, 시리즈마다 다른 가격을 주는 모의 Binance):

- 같은 계약·시간봉 동시 200명 → 공급자 호출 1회(577행 전체 구간), 200명 모두 같은 사본.
- 유효 기간(5m 15초) 안 50회 조회 → 추가 호출 0. 만료 후 동시 50명 → 갱신 1회, 꼬리 2행(가중치 1).
- 한 시리즈(ETH) 갱신 실패 → 그 시청자만 stale, 다른 시리즈(BTC) 시청자는 정상. 실패 시리즈는 15초 재시도 금지, 캐시 없는 실패 시리즈는 그 시청자만 503.
- 라우트 경유 30개 계정 → 공급자 호출 1회, 같은 응답 객체. 같은 시각 잘못된 요청(400)은 그 요청만 실패. 응답 키는 `candles, instrument, interval, priceBasis, range, source, state`뿐(계정 정보 없음).

### A-2 분당 120회 제한 — 이상 없음

같은 spec, 상한은 `readFuturesCandleProviderConfig({ FUTURES_CANDLE_PROVIDER_MAX_CALLS_PER_MINUTE: '120' })`로 운영값 명시(기본값 60은 변경하지 않음):

- 119개 시리즈 × 시청자 3명 동시 → 호출 119회(중복 미집계). 순차 실행이라 앞 40개 시리즈(120명)는 정상, 나머지 79개 시리즈(237명)는 정확히 8초에 503. 이들의 재시도는 끝난 갱신으로 응답(추가 호출 0).
- 정확히 120번째 → 허용. 121번째 이후 11개 → **즉시**(대기 0ms) 거절, 캐시 있는 시리즈는 stale, 없는 시리즈는 503, 공급자 호출 없음.
- 30초 무조회 동안 호출 0, 거절된 키 200회 연타에도 호출 0(무한 재시도·내부 재시도 타이머 없음).
- 첫 허용 후 59.999초에는 여전히 거절, 60초에 창이 이동해 12개 시리즈 정상 조회 재개.

### A-4 기존 Last/Mark 복구 보호 — **실제 문제 발견 → 최소 수정**

신규 `backend/src/providers/binance/binance-rest-chart-coexistence.integration.spec.ts`(opt-in, 기존 조정기 fixture와 같은 환경변수): 실제 `ProviderHttpClient` + 실제 Redis Lua 조정기(예산 1200) + 실제 차트 공급자(상한 120)·klines 파서, Binance만 모의(응답 80ms). Last 재확인(`/fapi/v2/ticker/price`, 가중치 2)·Mark 복구(`/fapi/v1/premiumIndex`, 가중치 10)는 운영 서비스와 같은 URL·타임아웃으로 3초마다 1건씩, 현물 캔들 수집은 2자산 병렬로 `/api/v3/klines` 300건(600).

**수정 전 측정**

| 상황 | 분 예산(Redis 카운터) | Last/Mark 예산 거절 | 복구 성공 간 최장 간격 |
| --- | --- | --- | --- |
| 정상(차트 3개) | 75 | 없음 | 3.0초 |
| 현물 수집만(3회) | 596~804 | 없음(슬롯 경합 BUSY 1~2회) | 4.7~8.5초 |
| 차트만 상한 120(2회) | 차트 520~600 | 없음 | 3.0~3.1초 |
| **현물 수집 + 차트 콜드 버스트가 같은 1분(2회)** | **1200 소진** | **Last 4~5회, Mark 5회** | **15.0~18.0초** |

→ 차트의 콜드 조회(5m 577행 = 가중치 5, 상한 120회면 분당 최대 ≈600)가 현물 수집(600)과 같은 분에 겹치면 공유 예산 1200을 다 써 버리고, 그 분이 끝날 때까지 Futures Last/Mark REST 복구가 `PROVIDER_RATE_LIMITED`로 거절된다. Mark 최대 허용 나이는 5초(`MARK_MAX_AGE_MS`)라 그동안 선물 주문·평가는 기존 정책대로 막힌다(안전하게 실패하지만, 차트 때문에 금융 시세 복구가 방해받음). 지속적이지는 않다(분이 바뀌면 회복, 거절된 차트는 다음 분까지 멈춤). 차트만으로는(현물 수집 없이) 방해가 없었고, 슬롯 경합(BUSY)은 차트와 무관하게 현물 수집의 2자산 병렬에서 생긴다.

**수정(최소, 구조·Lua 변경 없음)**: 차트 호출만 "분 예산 − 240"까지만 받는다. 240 = Last 재확인 1분치(20회×2) + Mark 복구 1분치(20회×10). 기존 ACQUIRE 스크립트가 호출마다 예산을 인자로 받으므로, 차트 호출일 때 그 인자를 `budget − 240`(1200이면 960)으로 넘긴다. 초과 시 기존 "예산 소진" 거절과 같아서 차트는 다음 분까지 멈춘다(재시도 폭주 없음). 다른 호출자(현물 수집·4h upkeep·Last·Mark)는 기존과 같이 전체 예산을 쓴다. 기본값 60·운영값 120·예산 1200은 그대로.

- `binance-rest-coordinator.ts`: `BINANCE_REST_RECOVERY_RESERVE_WEIGHT = 240`, `acquire(url, timeoutMs, reserveWeight = 0)`
- `provider-http.client.ts`: 옵션 `binanceReserveWeight` 전달
- `binance-candle.types.ts`·`binance-candle.ingestion.service.ts`·`binance-kline-usdm.client.ts`: 선택 필드 `reserveWeight` 통과(없으면 기존 호출과 완전히 같음)
- `market-candle-futures-provider.service.ts`: 모든 차트 호출에 `reserveWeight: 240`

**수정 후 측정**

| 상황 | 분 예산 | Last/Mark 예산 거절 | 최장 간격 |
| --- | --- | --- | --- |
| 현물 수집 + 차트 콜드 버스트 같은 1분 | 1116(차트는 320에서 멈춤) | **없음** | 3.5~3.7초 |
| 현물 수집 + 차트(정렬 안 함) | 1043 | 없음(BUSY 1회) | 4.2~4.3초 |
| 차트만 상한 120 | 차트 600 | 없음 | 3.0초 |
| 예산 958에서 차트 콜드(5) | — | 차트만 거절(HTTP 없음), 이어서 Last 1회·Mark 23회 허용(1190) | — |
| 예산 거의 소진(1196) | 1200 | 초과분 거절(안전 실패), 차트 39회 조회에 조정기 요청 1회, 다음 분 Last/Mark 즉시 회복·차트 재개 | — |

그 밖의 확인:

- 분 예산 초과 없음(Redis 카운터 최대 1200), 동시 실행 lease 최대 2, 차트 동시 실행 최대 1 — 모든 시나리오.
- Last/Mark가 유효하지 않을 때의 주문 차단: 차트는 Last/Mark를 쓰지도 쓰지도 않으므로 기존 정책 그대로. 기존 `futures-last-price.spec.ts`("fails closed without fallback")·`futures-mark.spec.ts`(5초 경계, WS 지연 시 REST 복구) 통과.
- 차트 데이터를 Last/Mark 대체 가격으로 쓰지 않음: 신규 소스 검사 — `futures/orders/positions/portfolio/batch/ranking/home/records` 어디도 차트 klines 모듈을 import하지 않고, 차트 공급자는 DB·Last/Mark 테이블에 쓰지 않는다.
- 이 WSL 호스트는 벽시계가 약 30초마다 약 2초 뒤로 간다. Redis TIME도 같이 움직여 로컬 시계 기준 분 합계가 1200을 넘어 보인 실행이 1회 있었다(조정기 자체 카운터는 1200 이하). 그래서 단언은 조정기의 Redis 카운터로 하고, 다음 분 대기도 Redis TIME이 실제로 넘어갈 때까지 기다리도록 했다(같은 원인으로 1회 실패 → 수정 후 통과, journal의 clock change 시각과 일치).

## B. 일반계정 초기화 후 과거 실현손익 정합성 — 이상 없음(코드 변경 없음)

정적 확인: 일반계정에서 실현손익이 보이는 곳은 포트폴리오 요약 `실현손익`(= 현물 `Position.realizedPnlKrw` 합), 선물 거래내역의 체결별 실현손익(이력), 열린 선물 포지션 카드뿐이다. 기록 탭 손익 분석·친구 거래 완료 종목·시즌 홈은 시즌 전용이다. 초기화는 보유·포지션이 있으면 거부되므로 기간을 걸친 열린 포지션은 없고, 비워진 현물 포지션의 실현손익만 0으로 재기준하며 이전 값은 초기화 행(`positionsRebasedJson`)에 남는다. 일별 이력은 기간 시작 이후만 읽는다(`epochStart`).

동적 확인: `backend/scripts/general-account-reset-integration.ts`에 시나리오 추가(CI의 core account 목록이 이미 실행하는 스크립트):

1. 초기화 직전 포트폴리오 `실현손익` = 초기화 행에 보존된 값(`realizedPnl`·`realizedPnlKrw` 모두 정확히 일치, 이익 R1 > 0).
2. 초기화 뒤 **같은 종목**을 다시 사고(120) 손실로 팔아(100) 같은 포지션 행을 재사용 → 행의 실현손익 = 이번 매도분 R2(< 0)와 정확히 일치(R1이 섞이지 않음), 원화 = R2 × 체결 환율, 포트폴리오 `실현손익` = R2 원화. 1차 초기화 행은 그대로.
3. 2차 초기화 행에는 R2만 보존(1차 값 중복 없음), 마감 총자산·누적 원금·투자 손익 = 직전 포트폴리오(1차 기간만). 2차 뒤 실현손익 0.
4. 1차 초기화 이전의 주문·원장 행 전부, 종료된 선물 포지션의 실현손익(7)이 처음 기록 그대로(행 단위 텍스트 비교).
5. 스크립트 끝의 읽기 전용 감사(`auditGeneralAccounts`) 발견 0건.

결과: 통과(로컬 PG16). 기존 시나리오(빈 계정·사용 계정·차단 사유·롤백·멱등·동시성·일별 작업·감사)도 같은 실행에서 통과.

## C. 국내주식·미국주식·암호화폐 현물 종목검색 바텀시트

- 종목 상세(국내·미국·암호화폐 현물) 이름 ▼가 전체화면 `종목 검색` 화면으로 이동하던 것을, 선물 상세가 주문 화면의 계약 선택 시트를 쓰는 것과 같이 **현물 주문 화면의 기존 종목 선택 시트(`OrderAssetSheet`)를 그 자리에서 연다**. 검색어·시장(전체/국내/미국/암호화폐)·정렬·실시간 시세 행은 주문 화면과 같다.
- 다른 종목을 고르면 `setParams({ assetId })`로 같은 상세를 그 종목으로 다시 만든다(이전 종목의 가격·통화 선택·차트가 남지 않음, 뒤로 가기 스택은 기존 `popTo`와 같음). 같은 종목은 시트만 닫는다. 화면이 포커스를 잃으면 시트를 닫는다(선물 상세와 같음).
- 마켓 탭의 검색 버튼 → `종목 검색` 화면은 그대로.
- 테스트: `AssetDetailFlow.test.ts` 기존 단언(▼ → MarketSearch 이동)을 시트 열림으로 바꾸고, 검색→같은 종목→다른 종목 교체 흐름 테스트 추가.

## 하지 않은 것 / 위험

- Render 환경변수 조회·변경, 배포, 운영 DB·Redis 접근, 실제 Binance 호출 — 하지 않음.
- 실기기·브라우저 화면 확인 안 함(단위·하네스 테스트만). 좁은 화면(320dp)에서 보유 행 이름 칸이 로고 폭(50dp)만큼 줄어 긴 이름의 줄바꿈이 늘 수 있다(잘림 없음).
- 종목 상세의 검색 시트는 주문 화면 시트와 같이 RN `Modal`이라 초보 퀘스트 안내 위에 그려진다(주문 화면과 같은 기존 동작). 상세 화면 퀘스트 단계는 시트를 쓰지 않는다.
- 슬롯 경합(현물 수집의 2자산 병렬이 Last/Mark 복구를 1~2회 BUSY로 늦추는 것, 최장 4.7~8.5초)은 차트와 무관한 기존 동작이라 이번 범위에서 바꾸지 않았다.
- 예비 가중치는 기존 조정기처럼 프로세스별 예산 기준이다. 같은 Redis를 쓰는 인스턴스가 여럿이면 각 프로세스의 차트가 공유 카운터 960까지 받으므로, 인스턴스를 늘릴 때는 기존 문서(binance-rest-limits.md)대로 예산·예비분을 다시 계산해야 한다(운영 인스턴스 수는 이번에 확인하지 않음).
