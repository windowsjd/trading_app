- 범위 전체가 달력상 휴장이면 공급자를 부르지 않고 `expected_no_data`로 그 범위를 증명한다([sync:1110-1119](../../../backend/src/assets/market-candle-sync.service.ts#L1110-L1119)).
- 달력이 없는 연도는 실패한다.

**판정**

- 조회기는 원천 범위 `[from, min(to, now))`에 대해 '완료·완전' 체크포인트의 union을 만든다.
- 판정 기준([loader:101-128](../../../backend/src/assets/candle-database.loader.ts#L101-L128), [:369-384](../../../backend/src/assets/candle-database.loader.ts#L369-L384)):

  | 상태 | 조건 |
  |---|---|
  | `complete` | union이 시작점에서 출발하고 끝까지 닿는다 |
  | `stale_tail` | 꼬리만 1일 이내로 비었다 |
  | `insufficient` | 그 밖 |

- 그 밖의 판정:
  - 범위와 겹치는 가장 최근 체크포인트가 완료가 아니면 '차단'이다.
  - 구성 봉이 빠진 집계 버킷은 버린다.

**제공** ([serving:292-405](../../../backend/src/assets/candle-serving.service.ts#L292-L405))

- 신선(60초)하고 신뢰할 수 있으면 DB를 그대로 준다.
- 아니면 관리형 sync를 돌린다(공급자 호출).
- sync가 실패하면 다음 순서로 내려간다: 오래된 캐시 → 엄격 LKG → `database_partial` → 오류.
- HTTP 응답에는 `available|empty`만 있다. 완전성은 밖으로 드러나지 않는다.

**KRX 원천**: 1분봉 어댑터는 KST 당일 세션만 조회하고, 시작이 개장 전이면 미완료로 본다. 그 결과가 F18이다.

### 4.2 최종 계약 (v2)

**원칙: '저장된 5분봉이 완전하다'는 주장은 체크포인트 증거로만 성립한다. 증거가 필요한 대상은 '필수 슬롯'뿐이다.**

- 필수 슬롯의 정의는 기존 집계 완전성 규칙과 같다([expected-slots:33-56](../../../backend/src/assets/candle-expected-slots.policy.ts#L33-L56)).
  - 5분봉: 정규 세션 `[개장, 마감 − 10분)`의 5분 격자. 종가 단일가 10분은 필수가 아니다.
  - 1d: 거래일마다 확정 일봉 하나.

**작성 규칙 (중앙 수집기, KRX 5m)**

1. **실행.** 틱마다 종목별로 `syncAsset({targets:['5m'], mode:'repair', from, to: now, resume:false, budget:{maxPages:2, maxRows:200, maxDurationMs:15000}})`를 부른다.
   - 기존 잠금, 체크포인트, 빌더, upsert를 그대로 쓴다.
   - `repair`는 넘긴 `from`을 그대로 쓴다.
   - `incremental`은 시작을 `최신 행 − 120분`으로 다시 계산해 frontier를 깨므로 쓰지 않는다.
2. **시작점.** `from = floor5(max(F, now − 90분, H))`. 내림해도 창이 95분 이하이므로 언제나 1회 호출이다(1분봉 요청 창은 95분 이하).
   - `F`: 당일 개장부터 연속 증명된 끝. `findCandleCoverage(asset, '5m', 개장, now).contiguousCoveredTo ?? 개장`
   - `H`: hold된 구멍의 끝. 없으면 무시한다.
3. **증명 조건(강화).** 실행 범위 안의 닫힌 필수 슬롯이 모두 '1분봉 5개 연속'으로 저장됐을 때만 `coverageComplete=true`로 기록한다.
   - upsert 뒤 DB를 확인한다. 기존 1d 저장 증거 감사([sync:826-866](../../../backend/src/assets/market-candle-sync.service.ts#L826-L866))와 같은 방식이다.
   - 1분봉이 한 줄도 없는 버킷도 잡는다(F26 해소).
4. **구멍(hold).** `F` 바로 뒤의 필수 슬롯이 닫힌 지 2틱(10분)이 지나도 불완전하면 hold한다.
   - 다음 틱은 그 슬롯 뒤에서 시작한다.
   - hold는 별도 테이블 없이 DB에서 매번 계산한다.
5. **장후 복구 (15:40, 당일 안).** 오늘 union의 공백 가운데 닫힌 필수 슬롯이 있는 것만 `[공백 시작, 공백 끝)`으로 다시 실행한다.
   - 상한: 공백당 2회, 종목당 3회, 전체 300회. 시도 횟수는 당일 체크포인트의 target 범위로 센다.
   - 상한 뒤에는 hold로 남기고 경보를 낸다.
   - 어댑터가 당일만 신뢰하므로 다음 날에는 복구하지 않는다.
6. **1d.** 15:50에 `syncAsset({targets:['1d'], mode:'repair', from: F_1d, to: now})`를 부른다. 기존 `inspectKisDailyEvidence`가 저장 일봉을 감사한 뒤에만 증명한다.

**조회 규칙 (KRX, 플래그 켜짐)**

7. **휴장 브리지.** `findCandleCoverage`에 선택 인자 `isBridgeableGap(a, b)`를 추가하고 KRX 5m·1d 피드에만 넘긴다.
   - union의 공백(시작 앞, 중간, 꼬리)이 아래 조건을 만족하면 이어진 것으로 본다.

     | 피드 | 브리지 조건 |
     |---|---|
     | 5m | 공백 `[a, b)`와 겹치는 필수 슬롯 가운데 이미 닫힌 것(`slot + 5분 ≤ now`)이 없다 |
     | 1d | `(a, min(b, now)]` 안에 세션 마감 시각이 없다. 즉 그 사이에 확정된 일봉이 없다 |

   - 달력에 없는 날짜가 끼면 거짓이다(fail-closed). 임시 휴장은 기존 운영자 override 층이 반영한다.
   - 브리지는 이미 union에 있는 거짓 증명을 걸러내지 못한다. 예: F26, 출처 필터 없이 섞인 KIS 시절 행.
     - 그래서 KRX 5m은 종목의 **수집 의무 시작 시각 `A`** 이전에 생성된 체크포인트를 증거에서 뺀다. 데이터는 바꾸지 않는다.
     - **(v2.1)** v2의 단일 '활성화 시각'을 종목별로 일반화했다(§5.6). 기존 15종목의 `A`는 플래그 활성화 시각이다.
     - `A` 이전 창은 지금처럼 `database_partial`로 나간다. 45일 보존이 지나면 사라진다.
   - 브리지는 조회 시점의 달력을 쓴다. 과거 날짜에 휴장 override를 나중에 넣으면 그날의 판정이 바뀐다. override 변경은 기존 감사 절차를 따른다.
   - 거래정지나 무체결 분이 있는 종목은 닫힌 필수 슬롯이 비므로 브리지되지 않는다. 그 창은 계속 `insufficient`(봉은 partial로 제공)다. 정확성 문제가 아니라 가용성 비용이다.
   - US·crypto와 다른 피드는 지금과 같다.
8. **신선도.** KRX는 `coverageStatus = complete`이면 신선하다. '존재할 수 있는 확정 데이터는 모두 증명됐다'는 뜻이다.
   - 장중에는 버킷이 닫힌 뒤 다음 틱까지 약 70초 동안 꼬리가 비어 `stale_tail`이 되고, 그 버킷의 미확정 행은 응답에서 빠진다(`database_partial`).
   - 다음 틱이 확정봉을 쓰면 기존 캐시 무효화로 바로 정상 응답이 된다.
9. **공급자 호출 금지.** KRX 요청은 관리형 sync, legacy 직접 조회, cold baseline 경로 어디서도 공급자를 부르지 않는다. 응답은 다음과 같다(오류 코드는 기존 코드를 쓴다).

   | 판정 | 응답 |
   |---|---|
   | 신뢰할 수 있음(complete 또는 stale_tail, 차단 없음, 버린 버킷 없음) | DB 그대로 |
   | 봉이 하나라도 있음 | `database_partial` |
   | 봉이 없음 | 503. 집계 간격(15m·30m·1h·4h)은 `ASSET_CANDLES_BASELINE_NOT_READY`, 5m·1d는 `ASSET_CANDLES_PROVIDER_UNAVAILABLE` |
   | `interval=1m`, 정책 밖 범위 | 503. 앱은 요청하지 않는다 |

10. **(v2.1) 부족 원인 분류 (로그 전용).** 5분봉을 원천으로 쓰는 KRX 창이 `A`보다 앞에서 시작하면, `[max(원천 시작, A), min(to, now))`를 규칙 7과 같은 방법으로 한 번 더 판정해 전달 로그에 남긴다. 대상은 5m·15m·30m·1h, 그리고 4h `96d`의 최근 30일 원천이다.

    | 분류 | 조건 | 응답 |
    |---|---|---|
    | `pre_obligation` (초기 이력) | `A` 이후 구간이 complete 또는 stale_tail이다. 부족한 곳은 `A` 이전뿐이다 | 지금과 같다: `insufficient` → 저장된 봉만 `database_partial` |
    | `post_obligation` (수집 결함) | `A` 이후 구간에 내부 공백이 있거나, `A` 직후부터 증거가 없다 | 같다 |
    | 분류 없음 | 원천 창이 `A` 이후에서 시작한다 | 기존 판정 그대로 |

    - 응답·신선도·캐시·공급자 호출 금지 규칙은 바뀌지 않는다. 분류는 G4 측정(§12.4)과 경보에만 쓴다.
    - 다시 판정하는 이유: 지금 `findCandleCoverage`는 union이 원천 시작점에서 출발하지 않으면 빈 결과를 돌려준다. 그래서 지금 로그(`coverageStatus`, `coveredTo`, `coverageInteriorGap`)로는 두 경우를 구분할 수 없다 [사실, [repository:295-315](../../../backend/src/assets/market-candle-sync-state.repository.ts#L295-L315)].
    - 1d 피드에는 적용하지 않는다. 1d는 활성화 전에 백필하므로(§5.4) 초기 이력 상태가 없다.

**브리지를 조회기에 둔 이유.** 작성기에 휴장 증명 실행(하트비트)을 두는 방식도 검토했다. 다음 세 가지 때문에 택하지 않았다.

- 동시호가 처리(F25)를 먼저 고쳐야 한다.
- 주말·연휴에도 작업이 정시에 돌아야 한다.
- 행이 늘어난다.

브리지 규칙이 따르는 기준은 기존과 같다. 작성기의 `expected_no_data`, 집계의 필수 슬롯 정의와 같은 달력·필수 슬롯 기준이다. 필수 슬롯 검사는 약해지지 않는다.

### 4.3 일곱 가지 검토 질문에 대한 답

| 질문 | 답 |
|---|---|
| 1. 중앙 수집 5분봉을 조회기가 어떻게 완전으로 인정하나 | 수집이 기존 `syncAsset`으로 체크포인트를 남긴다. 조회기는 기존 union에 KRX 휴장 브리지만 더해 같은 증거를 읽는다. 체크포인트 없이 저장하는 경로는 없다 |
| 2. 원본 1분봉 연속성과 기간 전체 완료 증거의 구분 | 연속성은 빌더(1분봉 5개 연속)와 증명 조건 3(닫힌 필수 슬롯 전부 저장)이 맡는다. '이 봉이 온전한가'다. 기간 완료는 체크포인트 union과 휴장 브리지가 맡는다. '이 기간에 빠진 봉이 없는가'다 |
| 3. 미완성 봉, 누락 구간, 정상 휴장의 구분 | 아래 세 줄 |
| | · 미완성: `isClosed=false`인 현재 버킷이다. 닫혔는데 갱신되지 않은 행은 응답에서 버린다 |
| | · 누락: 닫힌 필수 슬롯을 증명하지 못한 공백이다. 내부에 있으면 `insufficient`다 |
| | · 휴장: 필수 슬롯이 없는 공백이다. 브리지로 연결한다. 동시호가 10분도 같은 규칙을 따른다 |
| 4. 장중 증분과 장후 복구가 같은 상태를 갱신하나 | 둘 다 같은 `syncAsset`, 같은 잠금, 같은 테이블을 쓴다. union은 실행 순서와 무관하다. 복구가 성공하면 공백이 메워지고, 그전의 실패 행은 더 새로운 완료 행에 가려져 차단하지 않는다 |
| 5. 기존 이력과 공존할 때 충돌하지 않나 | 다음 네 가지로 정리된다 |
| | · KRX 5m: 수집 의무 시작 시각 `A`(§5.6) 이전 체크포인트는 증거에서 뺀다(F26 거짓 증명 차단). 그 이전 창은 지금처럼 partial로 나가고, 행은 45일 보존과 함께 정리된다(§4.4 ⑤) |
| | · 1d: 기존 완전 행은 날짜 감사를 거친 증거라 그대로 쓴다. 레거시 실패 행은 576세션 백필 실행(더 새롭고 범위를 포함)에 가려져 §4.4 ①로 정리된다 |
| | · 레거시 completed(coverageComplete=false) 행은 계속 무시한다 |
| | · 과거 창의 최신 겹침 행이 실패 행이면 그 창은 `incomplete`로 남는다. 봉은 partial로 그대로 나간다. 새 작성기는 활성화한 날부터 증거를 쌓는다 |
| 6. 장기 증거를 지키면서 행 증가를 막는 방법 | §4.4 압축. union을 바꾸지 않고, 날짜만 보고 지우지 않는다 |
| 7. 재시작·실패·중복 수집 시에도 정확한가 | 아래 세 줄 |
| | · 재시작: running 행은 잠금 TTL(120초) 뒤 다음 틱이 `SUPERSEDED`로 취소한다. 증명은 완료 시점에만 기록되므로 반쯤 쓴 증명은 없다 |
| | · 실패: 실패 행에는 증명이 없다. 다음 틱 범위가 그 범위를 포함하므로 곧 가려진다 |
| | · 중복: 자산·피드 잠금이 동시 실행을 막고 upsert는 멱등이다. 순차 중복은 같은 증명이 한 번 더 남을 뿐이다. 낭비되는 호출은 슬롯 키가 막는다 |

### 4.4 체크포인트 압축·보존 (v1 R8 대체)

**허용하는 연산**: union 결과와 '최신 겹침 행의 상태'(차단 판정)를 둘 다 바꾸지 않는 연산만 허용한다. 단, 압축 전 union이 2,000행 상한에 잘리던 창은 예외다. 그 창은 압축 뒤 실제 증거대로 판정된다(F19 해소). 숨어 있던 구멍이 드러날 수 있다.

**실행 조건**

- 매일 05:00 KST, 5분봉 보존 작업 뒤에 돈다.
- 자산·피드 잠금을 잡은 채로 처리한다.
- '오늘 00:00 KST 이전에 생성된 행'만 대상으로 한다.
- 활성 행(pending/running)은 건드리지 않는다.

| 단계 | 연산 | 결과가 바뀌지 않는 이유 |
|---|---|---|
| ① | 실패·취소 행 R을 지운다. 단, R보다 늦게 만들어진 완료 행 C가 R의 target 범위를 포함할 때만 | R과 겹치는 모든 창에서 C도 겹치고 C가 더 새롭다. R은 최신 겹침 행이 될 수 없고 증거도 아니다 |
| ② | ① 뒤에도 기준 시각 이전에 생성된 '완료가 아닌 행'(실패·취소·대기·실행 중)이 하나라도 남은 자산·피드는 ③④를 하지 않고 경보한다 | 진짜 미해결 실패는 그대로 남긴다. 실행 중 행도 포함하는 이유: `resume`은 생성 시각과 상관없이 오래된 실패 행을 되살린다([repository:160-172](../../../backend/src/assets/market-candle-sync-state.repository.ts#L160-L172)). 그런 행이 있을 때 ③이 그 행을 가리던 새 완료 행을 지우면 차단 판정이 바뀐다 |
| ③ | 증거가 아닌 완료 행(coverageComplete=false)을 지운다 | 남은 옛 행이 모두 완료 상태라 차단 판정이 그대로다. union에도 기여하지 않는다 |
| ④ | 겹치거나 맞닿은 완전 행 묶음을 1행으로 합친다 | union이 같다. 새 행의 생성 시각도 기준 시각 이전이라 이후 행과의 순서가 그대로다 |
| | · `covered = target = 묶음 union` | |
| | · `completedAt`·`createdAt` = 묶음의 최댓값 | |
| | · `cursorJson = {compacted:{rows, from, to}}`. 스키마 변경 없음 | |
| ⑤ | 보존 기간 밖 행을 지운다. 대상은 `targetTo`와 `coveredTo`가 둘 다 5분봉 보존 기준선 이하인 행이다. ②와 무관하게 수행한다 | 데이터가 이미 삭제됐다. 그 행은 기준선 이후를 포함하는 창과 겹치지 않는다. '관리 범위 ≤ 보존' 불변식이 있으므로 그런 창만 조회된다 |

**효과** [모델]

- 100종목 5분봉 체크포인트가 하루 약 8,100행에서 약 200행으로 줄어든다.
- 1h 창의 union 입력은 약 115행 이하로, 2,000행 상한의 6%다.
- 1d는 하루 1행씩 이어지므로 종목당 1행으로 수렴한다.

**구현 조건**

- ④의 삽입과 원본 삭제는 한 트랜잭션에서 한다. 조회기는 union과 최신 겹침 행을 각각 따로 읽는다([loader:104-124](../../../backend/src/assets/candle-database.loader.ts#L104-L124)). 원자적으로 바꾸면 어느 쪽 상태를 읽어도 결과가 같다.
- `newestCompletedAt`은 병합 뒤 바뀔 수 있다. KRX 신선도는 이 값을 쓰지 않으므로(규칙 8) 영향이 없다. 압축은 KRX 피드에만 적용하고, KRX 작성기는 `resume:false`만 쓴다.

**검증**: 무작위 체크포인트 집합(오래된 실행 중 행, 2,000행 초과 포함)에 대해 압축 전후의 `findCandleCoverage`·`findLatestOverlapping` 결과를 비교하는 속성 테스트로 확인한다(§10). 2,000행을 넘지 않는 창은 결과가 같아야 한다.

### 4.5 진행 중 캔들과 지연 (보완 7.4)

**역할 분리**

- 현재가(T초 슬롯)는 시세·견적·체결 신선도에만 쓴다.
- 캔들 OHLCV는 KOSCOM 1분봉에서만 만든다.
- 스냅샷으로 고가·저가·거래량을 합성하지 않는다.

**확정 5분봉 생성 시각**

- 버킷 `[t, t+5분)`은 `t + 6분 10초` 틱에서 확정되고, 실행 시간 몇 초가 더해진다.
- 70초는 KOSCOM 1분봉 공개 지연의 가정값이다 [미검증, Q13]. 측정한 p99에 10초를 더한 값으로 정한다.

**형성 중 봉**

- 틱 시점까지 완료된 1분봉으로 만든 미확정 5분봉(`isClosed=false`)이다.
- 그래서 차트 마지막 봉은 현재가보다 최대 약 5분 늦는다.
- 15m·30m·1h·4h의 현재 버킷은 이 미확정 봉을 포함해 조회 시점에 집계한다.

**원본이 늦을 때 다시 조회하는 기준**

1. 틱에서 막 닫힌 버킷이 불완전하면 다음 틱이 frontier부터 다시 가져온다. 추가 호출은 없다.
2. 2틱이 지나도 불완전하면 hold한다.
3. 장후 복구를 2회 시도한다.
4. 그래도 안 되면 영구 공백으로 남긴다(보간 없음).

**진행 중 1d**

- 당일 저장된 5분봉으로 조회 시점에 합성한다. 호출은 0회, 지연은 최대 약 6.5분이다.
- 종가 단일가는 15:50 확정 일봉이 이 합성 봉을 대체할 때 반영된다.

**제품 동작 변경 (명시)**

- 형성 중 봉 지연: 지금 운영은 차트를 보는 동안 60초 신선도와 5m 캐시 30초 때문에 약 1–2분 늦다. 이것이 약 5–6분으로 늘어난다.
- 진행 중 1d의 원천: 공급자 일봉(1d 캐시 최대 900초)에서 5분봉 합성으로 바뀐다.
- 더 빨리 갱신할 수 없는 이유:
  - 2.5분 주기: 6배치·5초 기준 하루 44,388건, 월 976,655건(98%)이다.
  - 1분 주기: 분봉만 하루 약 3.9만 건으로, 지금 안보다 약 3.1만 건 많다.

- 원천 최대 폭은 집계 간격의 4시간 패딩과 '조회일 24:00' 최악 시점을 포함한다([krx_sessions §2](calc/krx_sessions.out.txt)).

### 5.6 신규 종목의 초기 이력과 수집 의무 (v2.1 보완)

**유지하는 결정 (v2)**

- 5분봉 계열(5m·15m·30m·1h)은 백필할 수 없다. 앱이 과거 1분봉을 날짜 검증 없이 신뢰하지 않기 때문이다(어댑터 당일 한정).
- **신규 종목은 활성화한 날부터 쌓는다.**
  - 1h 창은 25번째 세션에 완성된다.
  - 그전에는 저장된 만큼만 보인다(`database_partial`, 보간 없음).
- 4h(96)·1d(576)는 활성화 직전 주말에 백필한다.
- baseline CLI는 `activeOnly: true`가 고정이다([candle-baseline-sync.ts:259](../../../backend/scripts/candle-baseline-sync.ts#L259)). 비활성 상태에서 미리 백필하려면 `--asset-id` 예외를 추가해야 한다.
- 활성화 시점에 1h까지 완전해야 한다면 별도 기능이 필요하다.
  - 내용: 과거 1분봉 날짜 검증 경로(일봉 O/H/L/C 대조)
  - 비용: 25세션 × 5창 × 85종목 = 10,625건
  - 기본안에는 넣지 않는다.

**(v2.1) 수집 의무 시작 시각 `A`**

정상적인 초기 이력 부족과 수집 결함을 가르는 기준 시각이다.

| 항목 | 규칙 |
|---|---|
| 정의 | 중앙 수집기가 그 종목의 장중 5분봉을 증명해야 하는 첫 시각. `A` 이전의 닫힌 필수 슬롯에는 수집 의무가 없다. `A` 이후의 닫힌 필수 슬롯은 모두 의무다 |
| 값 | 코호트 첫 세션 날짜의 00:00 KST 이하. 15m 이상의 원천 창은 4시간 패딩이 있어 개장 직전 시각으로 두면 하루 늦게 끝난다 |
| 기록 | 확대 단계(코호트)마다 `{A, 종목 목록}`을 버전 관리되는 설정에 넣는다. 종목 활성화(고정 유니버스 적용 스크립트)보다 먼저 배포한다. v2의 플래그 활성화 시각이 첫 코호트(기존 15종목)다 |
| 데이터에서 추론하지 않는 이유 | 지금 자산에는 활성화 시각이 없다. `assets`에는 `isActive`·`createdAt`·`updatedAt`뿐이고, 고정 유니버스 적용은 감사 기록을 남기지 않는다 [사실, [asset-universe-apply.ts](../../../backend/scripts/lib/asset-universe-apply.ts)]. '첫 체크포인트 시각'을 쓰면 초기 수집이 실패한 종목은 `A`가 뒤로 밀려 결함이 사라진다. 압축(§4.4 ③)과 보존(⑤)도 가장 오래된 행을 지운다 |
| 불변 | 배포한 코호트의 `A`는 바꾸지 않는다. 설정 검증 테스트가 과거 코호트 값을 고정하므로, 바꾸려면 테스트 변경이 리뷰에 드러난다 |
| 기록이 없을 때 | 코호트에 없는 활성 국내 종목은 첫 코호트의 `A`를 쓴다(fail-closed: 결함이 더 많이 보이는 쪽) |
| 수집 대상 | 중앙 수집기의 대상 = 활성 종목 중 `A ≤ now`인 것. 수집이 `A`보다 늦게 시작되면 그 사이는 결함으로 잡힌다 |
| 재활성화 | 비활성화했다가 다시 켜는 종목은 새 코호트로 등록한다. 비활성 기간에는 의무가 없다 |
| 스키마 | 변경 없음 |

**종목·간격별 상태**

| 상태 | 조건 | 응답 | G4 (§12.4) |
|---|---|---|---|
| 초기 이력 (`pre_obligation`) | 원천 창이 `A` 앞에서 시작하고, `A` 이후의 닫힌 필수 슬롯은 모두 증명됐다 | 저장된 봉만 `database_partial`. 합성·보간 없음. 완전하다고 표시하지 않는다(HTTP는 지금처럼 `available`/`empty`만 노출) | 결함 아님. G4-H 진행 상황으로 보고 |
| 수집 결함 (`post_obligation`) | `A` 이후에 증명되지 않은 닫힌 필수 슬롯이 있다(hold 포함) | 같다 | G4-I 결함 |
| 이력 준비 완료 | 원천 창 전체가 `A` 이후이고 결함이 없다 | 기존 판정 | 일반 기준 |

- 초기 이력 상태는 간격마다 저절로 끝난다. 원천 창이 `A` 이후로 넘어가면 분류 대상이 아니기 때문이다. 해제 작업은 없다.

  | 간격 | 정책 세션 | 초기 이력이 끝나는 세션 |
  |---|---:|---|
  | 5m | 3 | `A` 이후 4번째 세션 |
  | 15m | 6 | 7번째 |
  | 30m | 12 | 13번째 |
  | 1h | 24 | 25번째 |
  | 4h `96d` | 원천은 5분봉 30일 | `A` + 30일 4시간 이후. 4h 백필이 끝났어도 그전에는 `pre_obligation`이다. 봉은 저장 4h 행과 5분봉 집계로 모두 나온다 |
  | 1d | 576 | 해당 없음. 활성화 전 백필 완료가 조건이다(G4-H) |

**결함을 숨길 수 없게 하는 장치**

1. `A`는 데이터가 아니라 사전 기록에서 온다. 수집이 늦게 시작되거나 첫날 전부 실패해도 `A`는 그대로라 그 구간은 결함으로 남는다.
2. 분류는 `A` 이후 구간을 기존 규칙(union, 브리지, 필수 슬롯)으로 다시 판정한 결과다. 브리지와 필수 슬롯 규칙은 약해지지 않는다.
3. G4-I는 응답 로그가 아니라 DB 증거로 센다(§12.4). 아무도 차트를 열지 않은 종목의 결함도 잡힌다.
4. hold는 결함으로 센다. v2 G4처럼 hold가 있는 종목을 표본에서 빼지 않는다.

## 6. 현재가 주기와 체결 신선도 (필수 보완 C)

### 6.1 현재 동작 [사실]

**주기**

- 운영(라이브 꺼짐)에서는 인스턴스마다 `setInterval(3초)` 고정 주기로 돈다([ops-scheduler:84](../../../backend/src/ops/ops-scheduler.service.ts#L84)).
- 수집이 진행 중이면 그 틱은 건너뛴다. 그래서 유효 주기는 `ceil(D/I)·I`다.

**저장**

- 체결시각(`effectiveAt`)이 앞설 때만 새 행을 만들고 이벤트를 낸다.
- 수신 시각과 체결시각 차이가 300초를 넘으면 거부한다([normalizer:89](../../../backend/src/providers/koscom/koscom-normalizer.ts#L89)).

**판정** ([eligibility:774-796](../../../backend/src/providers/source-eligibility.policy.ts#L774-L796))

- 체결 기준 10초는 env로 바꿀 수 없다.
- 두 규칙을 모두 본다.
  - `capturedAt`: 경과 초를 내림해서 10을 넘으면 실패
  - KRX `effectiveAt`: 10초를 넘으면 실패
- `effectiveAt ≤ capturedAt`이므로 실제로는 거래소 체결시각 규칙이 결정한다.
- 새 체결이 없으면 행이 생기지 않는다. 그래서 수집이 정상이어도 한산한 종목은 적격성을 잃는다.

**지정가 경로 A**

- 매처가 5초마다 돈다.
- 제출 이후 체결이면서 10초 이내로 신선한 스냅샷만 쓴다([matching:432-482](../../../backend/src/orders/limit-order-matching.service.ts#L432-L482)).

**(v2.1) ER 계산 규칙** ([er_replay.py](calc/er_replay.py), [eligibility:716-796](../../../backend/src/providers/source-eligibility.policy.ts#L716-L796))

- 시각 t에 판정하는 행은 `capturedAt ≤ t`인 최신 행이다. 행은 체결시각이 앞설 때만 저장되므로, 최신 capturedAt 행이 곧 최신 체결 행이다.
- 행 i의 적격 구간은 `[max(c_i, e_i), min(c_{i+1}, e_i + 10초, c_i + 11초))`를 세션으로 자른 것이다.
  - `e_i + 10초`: KRX 체결시각 규칙
  - `c_i + 11초`: capturedAt 규칙(경과 초를 내림해 10 이하)
  - `max(c_i, e_i)`: 미래 시각 거부 규칙
  - 보통은 `e ≤ c`라 체결시각 규칙이 결정한다. 공급자 시계가 앞서면 capturedAt 규칙이 결정한다.
- v2와의 차이: v2 스크립트는 분모를 `마감 − 첫 행`으로 잡았고, 세션 시각을 넘기지 않으면 첫 행·마지막 행을 세션으로 썼다. Q2′ SQL과 `koscom_budget.py` §6 모델도 같았다.

- 동시성 3은 L2 부하 테스트와 소규모 실측으로 KOSCOM 허용을 확인한 뒤에만 쓴다.

### 6.5 주기 선택 규칙 (v2.1 보완)

**증거 수준.** 같은 'ER_6'이라도 근거가 다르다. 보고서와 승인 자료에는 값과 함께 수준을 적는다.

| 수준 | 값 | 얻는 법 | 남는 가정 | 쓰임 |
|---|---|---|---|---|
| 관측 | ER_3 | 운영 3초 행(Q2′) | 없음. 그 세션의 사실이다 | 기준선 |
| 추정 ① | ER_6 행 재구성 | Q2″ 행 → `er_replay.py` | A1·A2·A3 (아래) | 선별에만 쓴다 |
| 추정 ② | ER_6 폴링 로그 재구성 | 단계 1 폴링 로그(Q2‴) → `er_replay.py --polls` | A2 | 시험 운영 대상 주기 선택 |
| 모델 | ER_4·ER_5 | §6.3 모의 | 체결·지연 분포 | 참고 |
| 실측 | ER_T | 실제로 T초로 수집한 세션 | 없음 | **최종 근거** (L1과 함께) |

- A1: 공급자 응답의 최신 체결이 이전 폴링보다 과거로 돌아가지 않는다. 역전이 생겨도 행이 저장되지 않아 행으로는 보이지 않는다.
- A2: 같은 시각의 6초 폴링은 3초 폴링과 같은 응답을 받는다. 실제 6초 운영은 위상, 부하, 응답 지연이 다르다.
- A3: 배치의 어느 종목도 행을 남기지 않은 회차도 폴링 자체는 성공했다. 행만으로는 '새 체결 없음'과 '수집 실패'가 같아 보인다.
- 재구성 방법(추정 ①)은 v2와 같다.
  - 같은 배치의 행은 같은 `capturedAt`을 공유하므로 사이클 시각을 복원할 수 있다.
  - 사이클을 하나 걸러 두 위상의 ER_6을 계산한다. 둘 다 유효한 6초 일정이다.
  - 행이 없는 회차는 설정된 주기로 보간해 다시 넣는다. v2는 주기를 행 간격의 중앙값으로 추정했는데, 저유동 배치에서는 틀릴 수 있어 설정값을 쓴다.
- 5초는 3초의 배수가 아니다. 그래서 어떤 수준으로도 재구성할 수 없고, 모델 값만 있다(모델상 6초 손실의 약 35–55%).

**폴링 로그 (Q2‴, 단계 1 진단 계측)**

- 기본은 꺼져 있고, 측정 세션에만 켠다.
- 배치·사이클마다 구조화 로그 1줄을 남긴다. 내용: 슬롯, 배치, 요청 시작·수신 시각, 성공 여부, 종목별 응답 체결시각(저장 여부와 무관).
- DB에는 쓰지 않는다(디스크 P0). 15종목·2배치·3초 기준 하루 약 15,600줄이다.
- `symbol,received_s,effective_s` CSV로 바꿔 `er_replay.py --polls`에 넣는다. A1(역전 횟수)과 A3(실패 회차)가 측정값이 된다.

**재구성 정확도** [모델, [er_replay 출력](calc/er_replay.out.txt) B]

합성 세션으로 확인했다. 조건: 5종목(초당 5·1·0.5·0.2·0.05회 체결), 개장 15초 뒤 첫 수집, 60초 수집 실패, 저유동 종목만 있는 배치, 지연 p99 1.0초·2.5초 두 가지.

| 비교 | 결과 | 뜻 |
|---|---|---|
| 폴링 로그 재구성 vs 같은 응답의 6초 폴링 | 0.000%p | 계산 경로가 맞다. A2가 성립하면 정확하다 |
| 행 재구성 vs 같은 응답의 6초 폴링 | ≤ 0.036%p | A1 위반(느린 지연에서 역전 최대 15회)과 보간 오차. 합성에서는 작지만 운영에서도 그런지는 모른다 |
| 재구성(두 위상 평균) − 실제 6초 폴러 20회 평균 | −0.19 … +0.10%p | A2로 생기는 치우침 |
| 실제 6초 폴러끼리의 흩어짐(sd) | 0.006–0.195%p | 한 세션 값에 섞이는 우연 |
| 한 위상 재구성 vs 실제 6초 폴러 1회 | 최대 0.84%p. 초당 1회 이상 종목은 ≤ 0.17%p | 단일 세션·단일 위상 값의 최대 오차 |

- 그래서 6초 재구성은 **정확한 재현이 아니다.** 초당 1회 이상 종목은 약 0.2%p, 저유동 종목은 약 0.5–0.8%p의 오차를 감안해야 한다.
- v2의 '0.01%p 이내 일치'는 같은 응답을 가정하고, 두 위상 중 가까운 쪽과 비교한 값이었다.
- 운영 데이터에서의 재구성 정확도는 증명되지 않았다. 증명하려면 같은 종목을 실제 6초로 수집해 비교해야 한다(아래 선택 순서 3).

**판정 기준** (기본값, 제품이 조정할 수 있다. §13 P4)

- (a) ER_3 ≥ 95%인 종목은 모두 `ER_3 − ER_T ≤ 1.0%p`
  - 세션 평균으로 본다. 재구성 값은 두 위상 중 나쁜 쪽을 쓴다.
- (b) ER_3 < 95%인 종목은 주기와 상관없이 자주 실패하는 저유동 종목이다. 유니버스에 넣을지는 제품이 따로 정한다.
  - **(v2.1)** 마감 단일가가 분모에 들어가 ER 상한이 약 97.4%다. 그래서 같은 95%라도 v2 모델보다 엄격하다(§6.3).
- (c) L1 부하 테스트에서 `D_p99 ≤ T − 1초`, 사이클 누락 ≤ 0.5%, 큐 타임아웃 0
- (d) **(v2.1)** 3초 기준선이 없는 종목(처음부터 T초로 수집한 종목)은 `ER_T ≥ 94%`(= 95% − 1.0%p). 못 미치면 (b)처럼 제품이 정한다.

**측정 표본 (v2.1)**

- 종목마다 5세션 이상을 쓴다.
- degraded 세션과 관측 기간이 불완전한 종목-세션은 뺀다(§6.2).
- 판정은 세션 평균으로 한다. 세션별 값과 두 위상 값을 함께 보고한다.

**선택 순서**

1. 50종목까지는 3초를 유지한다. 예산이 허락하고(F@50, 3초: 월 78%) 적격성 손실이 0이다.
   - 단, 3–4배치를 3초 안에 돌리려면 평균 응답 지연이 0.69초 이하여야 한다(동시성 2). 동시성 4면 1.09초까지 된다[모델, calc §5]. Q10에서 이를 넘으면 그 단계는 4초로 한다.
2. **(v2.1) 선별.** 50종목 단계의 3초 데이터로 ER_3(관측)과 ER_6(추정 ②. 폴링 로그가 아직 없으면 추정 ①)을 계산한다.
   - 오차 여유를 더해도 (a)를 지키는지 본다: `ER_3 − ER_6(나쁜 위상) + 여유 ≤ 1.0%p`.
   - 여유는 합성 검증에서 본 단일 세션 최대 오차다. 초당 1회 이상 종목 0.2%p(관측 최대 0.17), 초당 0.2–0.5회 종목 0.6%p(관측 최대 0.51). 그보다 드문 종목은 대개 (b)에 속한다.
   - 선별 결과는 시험할 주기를 고르는 데만 쓴다. 이것만으로 주기를 확정하지 않는다.
3. **(v2.1) 시험 운영(실측).** 선별을 통과한 주기(6초. 안 되면 5초)로 50종목을 3세션 이상 실제로 수집해 ER_T를 잰다.
   - 예산: F@50 6초 월 44%, 5초 월 50%([calc §9](calc/koscom_budget.out.txt), §7.2).
   - 직전 5세션의 3초 기준선과 비교해 (a)–(d)를 판정한다.
   - 시험 기간에는 일부 종목의 ER이 낮아질 수 있다. 제품 동작 변경이라 §13 P4 승인이 필요하다.
   - 실패하면 3초로 되돌린다. 50종목은 3초 예산 안이다. 6초가 실패하면 5초로 다시 시험한다.
4. **확대.** 실측으로 (a)–(d)를 통과한 T와 L1 통과(그 T로 100종목 부하)를 근거로 100종목에 간다.
   - 100종목에서는 3초로 되돌릴 수 없다(월 122%). 그래서 주기 실측은 50종목 단계에서 끝낸다.
   - 확대 뒤에도 ER_T를 계속 재고, G6 중단 기준에 쓴다.
5. 5초도 (a)를 어기면 다음 중 하나를 결정한다. (a) 위반은 금융 안전 문제(오래된 가격 체결)가 아니라 시장가 실패 증가다. 위반 종목과 감소폭을 보고하고 결정한다.
   - 해당 종목 제외
   - 4초 + 분봉 10분. 6배치에서 월 87%라 권하지 않는다.
   - 유니버스를 80–90종목으로 축소
   - 계약 상향

**10초 체결 신선도 기준은 바꾸지 않는다.** 주기 결정을 신선도 기준 완화로 보완하지 않는다(§6.6).

### 6.6 실패 시 동작 (기존 fail-closed 유지)

- 지연·누락·실패가 나면 그 슬롯은 건너뛰고 재시도하지 않는다.
- 가격이 10초를 넘으면 체결 API는 기존 오류(`PRICE_STALE`/`ASSET_PRICE_UNAVAILABLE`, 503)를 낸다.
- 표시(300초)와 견적(60초)은 각자 기준으로 계속 판정한다.
- 금지:
  - 오래된 공급자 가격의 시각을 새 시각으로 바꾸기
  - 신선도 기준 완화
  - 다른 원천의 가격으로 대체 체결
- 체결이 드문 종목은 주기와 상관없이 마지막 체결 10초 뒤부터 시장가가 불가하다(기존 정책, F17).

- 월 한도 영향: 1% 남짓이다.

### 7.5 인스턴스별 폴링 (보완 7.1)

**사실 관계** [사실]

- 라이브 꺼짐 모드에서는 모든 인스턴스가 고정 주기 타이머를 돌린다([ops-scheduler:74-87](../../../backend/src/ops/ops-scheduler.service.ts#L74-L87)). 스케줄러 설정 확인보다 먼저 등록되므로 스케줄러가 꺼진 인스턴스에서도 돌고, 부팅 직후 1회 바로 수집한다.
- 수집 잠금(`koscom:{ns}:ingestion`, 60초)은 사이클이 끝날 때마다 풀린다([ingestion:105-108](../../../backend/src/providers/koscom/koscom-ingestion.service.ts#L105-L108), [:253](../../../backend/src/providers/koscom/koscom-ingestion.service.ts#L253)).
- 슬롯 키도, 마지막 실행 확인도 없다.
- 그래서 A가 사이클을 끝내고 잠금을 푼 뒤 B의 틱이 오면, B가 같은 주기 안에서 한 사이클을 더 돈다.

| 상황 | 현재 | 최종안 |
|---|---|---|
| 1대 | 주기당 1회 | 1회 |
| N대 상시 | 타이머 위상에 따라 주기당 1~N회. 위상은 재배포 전까지 고정이다. 가격 행은 effectiveAt로 중복 제거되고, 호가 행은 중복 저장된다 | 슬롯 키로 주기당 1회 |
| 배포 겹침 | 겹치는 동안 최대 2배 | 1회 |
| 소유 인스턴스 비정상 종료 | 잠금이 최대 60초 남는다. 그동안 수집이 없어 체결이 fail-closed된다 | 잠금 TTL 3T, 공백 ≤ 3T |
| 수집 시간 > 주기 | 다음 틱을 건너뛴다(그 구간 유효 주기 2T) | 같다. `D_p99 ≤ T − 1초`를 부하 테스트 통과 조건으로 둔다 |
| 라이브 모드 켬 | 소유권 lease(30초)로 1대만 '수집 후 대기' 방식으로 돈다. 분봉 조회가 자동으로 시작된다 | KOSCOM 루프를 전역 라이브 플래그에서 떼어 낸다(F7) |

- 호출 상한은 전역 입장 제어가 막는다. 동시 2건, 시작 간격 200ms다.
- 따라서 '인스턴스 수에 비례'는 상한이고, 실제 배수는 1~N 사이다.

### 7.6 재시도·반복 경로와 예산 소진 (보완 7.3)

| 경로 | 현재 상한 [사실] | 분류 | 최종안 |
|---|---|---|---|
| 클라이언트 재시도 | timeout·network·5xx면 500ms 뒤 1회(최대 2시도). 429는 재시도하지 않고 공유 쿨다운 10초 | 횟수 | 가격은 0회(다음 슬롯이 재시도 역할). 나머지는 유지. 모든 시도를 예산에 센다 |

| 정기 sync | 600초마다, 24시간, 1d·1w를 매번 | 시간 경계 | KRX는 대상에서 뺀다 |
| 관리형 on-demand | 요청마다(캐시 TTL·단일 비행 아래), DB 신선도 60초 | 요청 비례 | KRX는 0 |
| long sync held | 실행당 ≤60회. 5세션 창 안에서 900초마다 다시 조회 | 창 경계 | 다음 거래일 1회 |
| LOC 증거 | 종목·세션당 최대 약 33회. 300초 간격, 마감 + 3시간 기한 | 횟수·기한 | 유지 |
| 정책 밖 직접 조회 | 요청당 최대 5페이지, 사용자별 제한 없음 | 요청 비례 | KRX는 0(503) |

**예산 소진 시 줄이는 순서**

1. P4를 멈춘다: 백필, 4h, 1w, 운영자 작업.
2. P3를 줄인다.
   - 1분봉 틱을 10분 주기로 바꾼다.
   - 그다음 장후 최종 틱만 남긴다.
   - 당일 갭 복구는 남은 예산 안에서만 한다.
3. P2(1d, LOC, recoverClose)는 hard cap 전까지 줄이지 않는다.
4. P1은 hard cap에 닿았을 때만 남은 예산이 허락하는 주기로 늦춘다.
   - 10초 이상이 되면 시장가 체결은 fail-closed가 된다. 표시·견적은 계속된다.
   - 예산이 0이면 모든 호출을 멈추고 가격이 오래된 상태(fail-closed)가 된다.

**한도를 넘는 호출은 하지 않는다.**

### 8.4 원문 JSON과 호가의 사용처

**원문 JSON**

- 명시적으로 읽는 곳은 한 곳뿐이다. 회전율 정렬([asset-list-turnover.ts:28-73](../../../backend/src/assets/asset-list-turnover.ts#L28-L73))이 `payload.row.accTrdval`과 `truncated === false`를 읽는다.
- 체결 트랜잭션은 id로 전체 행을 읽지만 원문을 해석하지 않는다.

**원문 축소안**

- 새 행에만 적용한다.
- `{row:{trdDd, trdTm, trdPrc, cmpprevddPrc, cmpprevddTpCd, accTrdvol, accTrdval, bidordPrc_1, askordPrc_1}, market, dateBasis, changeRate, truncated:false}`만 남긴다.
- 감사 영향: 나중에 다른 원문 필드를 다시 도출할 수 없다. 금융 판정에 쓰는 값(가격·시각·전일비)은 별도 컬럼과 위 필드에 남는다.

**호가**

- `koscom_krx_orderbook` 행을 읽는 곳은 0곳이다.
- KIS hoga 중복 검사만 KIS 행을 읽는다.

### 8.6 캔들·sync-state 보존과 완전성의 관계

- 5분봉 보존(45일)과 체크포인트 정리(§4.4 ⑤)는 같은 기준선을 쓴다. 그래서 증거가 지워진 데이터를 가리키거나, 데이터가 남았는데 증거만 사라지는 일이 없다.

### 8.8 100종목 전 최소 조치와 장기 최적화

**최소 조치 (100종목 전)**

1. Q1로 테이블별 크기와 하루 증가량을 측정한다. **오늘 바로 해야 한다.**
2. KOSCOM 호가 수집과 저장을 끈다(코드 플래그).
3. 새 가격 행의 원문을 축소한다.
4. health의 전체 COUNT를 추정치로 바꾼다.
5. 체크포인트 압축을 시작한다(§4.4).
6. 디스크 여유를 확보한다(증설 또는 자동 확장, 승인 필요).
7. 가격 스냅샷 보존 dry-run으로 지울 수 있는 양을 보고한다.

**장기 최적화**

1. 가격 스냅샷 보존을 정기 작업으로 돌린다(승인 뒤).
2. 기존 KOSCOM 호가 행을 정리하고 공간을 회수한다(승인 뒤).
3. `ops_job_runs`·`quotes` 보존 정책을 세운다. 이번 범위 밖이며 기존 감사 TC-E03과 묶는다.

|---|---|
| < 70% | 정상. 주간으로 크기를 측정한다 |
| 70–80% (**지금 74%**) | 근거 없는 증가원을 막는다: 호가 저장 중단, 원문 축소. 디스크 증설안을 승인받는다 |
| 80–90% | 승인된 정리를 한다: KOSCOM 호가 행 삭제, 보존 기간을 넘긴 미참조 가격 스냅샷 삭제. 디스크를 증설한다 |
| ≥ 90% | 즉시 디스크를 증설한다(Render 디스크·플랜 변경, 비용 승인). 종목 확대를 멈춘다 |

**공간 회수 방식**

- 행을 DELETE해도 OS로 공간이 돌아오지 않는다. 같은 테이블 안에서만 재사용된다.
- 호가 테이블은 KOSCOM 행이 대부분이다 [추론, Q1로 확인]. 두 가지 방법이 있다.
  - KIS 행만 남기고 비운다(TRUNCATE 또는 재작성).
  - 배치 DELETE 뒤 `VACUUM FULL`. 남는 행이 적으면 필요한 여유 공간도 작다.
- 대량 DELETE는 WAL을 만든다. 디스크 여유가 적을 때는 TRUNCATE 방식이 안전하다.
- 어느 방법이든 운영 데이터 삭제다. **별도 승인**을 받고 점검 시간에 한다.

**절대 지우지 않는 것**

- 참조된 스냅샷
- 세션 종가 증거
- 시즌 정산 증거
- `admin_manual` 행
- 원장과 주문 기록

**L10-A 장중 증분 수집**

- 목적: 장기 이력이 갖춰진 상태에서, 중앙 수집이 26세션 동안 최근 분봉·장기 봉·완전성 증거를 잇고 유지하는지 본다.
- 사전 상태 (fixture)
  - 종목 4개(코스피 2, 코스닥 2). 3개는 기존 코호트, 1개는 신규 코호트다. 신규 코호트의 `A`는 재생 2번째 세션 00:00 KST이고, 4h·1d만 백필돼 있다.
  - 1d: 576세션 확정 일봉과 그 범위를 덮는 완전 1d 체크포인트(날짜 감사를 통과한 상태). 2024 달력 포함.
  - 4h: 96세션 저장 4h 행과 long sync 완료 기록. 1개 세션은 `DAILY_REFERENCE_UNAVAILABLE`로 held.
  - 5m(기존 코호트): `A`를 사전 5분봉보다 앞에 둔다. 직전 25세션의 5분봉과, 그 뒤에 생성된 중앙 수집 체크포인트(압축된 형태)를 넣는다.
- 재생: 26세션. 장중 틱과 장후 작업이 실제 스케줄러 경로로 돈다(가짜 시계).
  - 창은 2개다. W1은 추석·개천절 대체·한글날(2026-09-24…10-09)을, W2는 수능일(2026-11-19, 10:00–16:30)을 포함한다.
  - 두 날짜는 약 37세션 떨어져 있어 한 창에 넣을 수 없다 [사실, krx-2026].
- 주입: 세션 5에 1종목 1분봉 3개 누락(hold), 세션 9에 실행 중 재시작, 세션 12에 장후 복구로 메워지는 일시 누락
- 통과 기준 (세션마다, 그리고 마지막에)
  1. 기존 코호트, 주입 결함이 없는 창: 5m 3·15m 6·30m 12·1h 24·4h `96d`·1d 576 응답이 모두 `complete`다. 버린 버킷 0.
  2. 신규 코호트: 간격마다 §5.6 표의 세션 전까지는 `pre_obligation`이고 저장된 봉만 반환한다(합성 봉 0). 그 세션부터는 `complete`다. 1h는 재생 26번째 세션에 `complete`가 된다.
  3. hold 주입: 그 구간을 포함하는 창은 `post_obligation`이다. 공백이 정확히 주입 구간이고 경보가 1건이다. 장후에 메워진 일시 누락은 공백을 남기지 않는다.
  4. 4h `96d`: 반환 버킷 수 = 기대 버킷 수 − held 세션의 버킷 수. 30일 밖 held 세션은 빈칸이다(보간 0). 버킷마다 원천은 하나다.
  5. 1d: 매 세션 장후 확정 1d가 1행씩 늘고, 체크포인트 union이 끊기지 않는다.
  6. 증거 유지: 매일 압축한 뒤에도 2,000행 이하 창의 판정이 압축 전과 같다. 보존 기준선 밖 행만 지워진다. 마지막 체크포인트 행 수 ≤ 종목 × (보존 세션 + 당일 틱).
  7. 호출: 장중 1분봉 = 종목 × 79/세션(+ 주입 재시도). KRX 조회발 공급자 호출 0.

**L10-B 초기 백필**

- 목적: 장기 이력이 없는 종목에 기존 4h·1d 백필 경로로 이력을 만들고, 완성 전과 후의 조회를 구분하는지 본다.
- 사전 상태: 종목 4개. 1d·4h·5m 행과 체크포인트가 없다. KRX 2024 달력은 있다. 코호트 `A` = 백필 다음 첫 세션 00:00 KST.
- 실행: 비거래일(주말 쿼터일)에 1d 576 백필(`syncAsset` 1d repair, 범위 명시) → 1d 저장 뒤 4h 96 long sync. 예산 관리자 켬.
- 주입
  1. 1d 한 페이지에 5xx 2회(재시도로 성공)
  2. 4h 한 세션의 10분봉이 일봉과 불일치(held)
  3. 백필 도중 프로세스 재시작
  4. soft cap에 닿게 해 백필 일부 차단(다음 쿼터일에 재개)
- 통과 기준
  1. 호출 수: 1d ≤ 종목당 7페이지, 4h ≤ 97세션 + 재시도 상한. 합계가 §7.4 단가의 ±5%다.
  2. 완료 판정: 1d는 §5.4의 두 조건(완전 체크포인트, 행 수 = 기대 세션 수)이다. 4h는 long sync `synced`이거나, `partial`이면 held 목록이 주입한 세션과 정확히 같다.
  3. 완료 전 조회: 1d 576 창은 `insufficient` → 저장된 만큼 `database_partial`, 공급자 호출 0. 완료 뒤에는 `complete`다.
  4. 4h `96d`: 백필 직후에도 5분봉 30일 증거가 없어 `pre_obligation`이다(정상). 봉 개수는 저장 행 기준으로 맞다.
  5. 실패 복구: 재시작 뒤 이어서 끝난다. 중복 행 0, 반쯤 쓴 증명 0.
  6. 멱등: 다시 실행하면 1d 공급자 호출 0(완료 판정을 먼저 본다), 4h 호출 ≤ held 세션 수(다음 거래일 1회 규칙). 행 수와 값은 그대로다.
  7. 예산: 차단된 백필은 P4로 기록되고, P1·P2 호출은 차단되지 않는다.

L10-A와 L10-B는 서로의 통과 기준을 대신하지 않는다. 테스트 파일 구성과 fixture 생성 방법은 실제 코드 구조에 맞춰 구현 담당자가 정한다.

모의 테스트를 통과해도 운영 검증이 끝난 것은 아니다. 실제 지연·오류율·한도 단위는 단계 1 계측과 단계 5 관찰로 확인한다.

-- Q1 DB·테이블 크기와 증가 (P0). 24시간 간격으로 두 번 실행해 차이를 본다
SELECT now(), pg_size_pretty(pg_database_size(current_database())) AS db;
SELECT c.relname, pg_size_pretty(pg_total_relation_size(c.oid)) AS total,
       s.n_live_tup, s.n_dead_tup, s.n_tup_ins, s.n_tup_del
FROM pg_class c JOIN pg_stat_user_tables s ON s.relid = c.oid
ORDER BY pg_total_relation_size(c.oid) DESC LIMIT 15;

-- Q2' (v2.1) 종목별 체결 적격 비율(ER_3, 세션 전체 분모)·S 분포·행 간격 (한 세션)
-- :open_utc/:close_utc = 그 세션 개장·마감의 UTC naive 값(달력 기준. 첫 행·마지막 행이 아니다)
-- :ids = 측정 대상 종목 id 배열. 행이 없는 종목도 ER 0으로 남는다
WITH ids AS (SELECT unnest(:ids) AS asset_id),
carry AS (  -- 개장 직전 최신 행 = 개장 시점의 상태
  SELECT DISTINCT ON (p.asset_id) p.asset_id, p.captured_at AS c, p.effective_at AS e
  FROM asset_price_snapshots p JOIN ids ON ids.asset_id = p.asset_id
  WHERE p.source_name = 'koscom_krx_realtime_price' AND p.captured_at < :open_utc
  ORDER BY p.asset_id, p.captured_at DESC),
r AS (
  SELECT x.*, lead(x.c) OVER (PARTITION BY x.asset_id ORDER BY x.c) AS nxt
  FROM (SELECT asset_id, c, e FROM carry
        UNION ALL
        SELECT p.asset_id, p.captured_at, p.effective_at
        FROM asset_price_snapshots p JOIN ids ON ids.asset_id = p.asset_id
        WHERE p.source_name = 'koscom_krx_realtime_price'
          AND p.captured_at >= :open_utc AND p.captured_at < :close_utc) x),
sp AS (  -- 행마다 적격 구간 [s0, s1): 미래 시각, 체결시각 10초, capturedAt 11초(내림 ≤10), 세션 경계
  SELECT r.*, greatest(r.c, r.e, :open_utc) AS s0,
         least(coalesce(r.nxt, :close_utc), r.e + interval '10 second',
               r.c + interval '11 second', :close_utc) AS s1
  FROM r)
SELECT a.symbol,
  count(sp.c) FILTER (WHERE sp.c >= :open_utc) AS rows,
  round((100 * coalesce(sum(greatest(0, extract(epoch FROM sp.s1 - sp.s0))), 0)
         / extract(epoch FROM :close_utc - :open_utc))::numeric, 2) AS er_pct,
  round((100 * coalesce(sum(greatest(0, extract(epoch FROM
             least(sp.s1, :close_utc - interval '10 minute') - sp.s0))), 0)
         / extract(epoch FROM :close_utc - interval '10 minute' - :open_utc))::numeric, 2) AS er_cont_pct,
  percentile_cont(ARRAY[0.5,0.95,0.99]) WITHIN GROUP (ORDER BY extract(epoch FROM sp.c - sp.e))
    FILTER (WHERE sp.c >= :open_utc) AS s_p50_p95_p99,
  percentile_cont(ARRAY[0.5,0.95,0.99]) WITHIN GROUP (ORDER BY extract(epoch FROM sp.nxt - sp.c))
    FILTER (WHERE sp.c >= :open_utc) AS gap_p50_p95_p99
FROM ids JOIN assets a ON a.id = ids.asset_id
LEFT JOIN sp ON sp.asset_id = ids.asset_id
GROUP BY a.symbol ORDER BY er_pct;

-- Q2'' (v2.1) 재구성용 행 내보내기 (한 세션, 개장 직전 이월 행 포함). CSV로 저장해 calc/er_replay.py에 넣는다
SELECT a.symbol, extract(epoch FROM x.c) AS captured_s, extract(epoch FROM x.e) AS effective_s
FROM ((SELECT DISTINCT ON (p.asset_id) p.asset_id, p.captured_at AS c, p.effective_at AS e
       FROM asset_price_snapshots p
       WHERE p.asset_id = ANY(:ids) AND p.source_name = 'koscom_krx_realtime_price'
         AND p.captured_at < :open_utc
       ORDER BY p.asset_id, p.captured_at DESC)
      UNION ALL
      (SELECT p.asset_id, p.captured_at, p.effective_at
       FROM asset_price_snapshots p
       WHERE p.asset_id = ANY(:ids) AND p.source_name = 'koscom_krx_realtime_price'
         AND p.captured_at >= :open_utc AND p.captured_at < :close_utc)) x
JOIN assets a ON a.id = x.asset_id
ORDER BY x.c;

-- Q4' 국내 1d 유지·백필 상태
SELECT a.symbol, count(m.*) FILTER (WHERE m.is_closed) AS closed_1d, min(m.open_time) AS oldest,
       max(m.open_time) FILTER (WHERE m.is_closed) AS latest_closed, max(m.source_updated_at) AS updated
FROM assets a LEFT JOIN market_candles m ON m.asset_id = a.id AND m.interval = '1d'
WHERE a.asset_type = 'domestic_stock' AND a.is_active
GROUP BY a.symbol ORDER BY latest_closed NULLS FIRST;

-- Q6' KRX 체크포인트 실태 (F18·F19)
